## Python-обработка

- Python detector не является блокирующим для первого MVP: сервер и LLM должны принимать уже подтверждённые пользователем пики независимо от способа их получения.
- Основной источник истины для отправки — только `stripeSets.confirmed`; `candidates` никогда не отправлять в интерпретацию как финальные данные.
- Для каждого подтверждённого пика передавать: `nu`, ширину/FWHM, относительную или нормализованную интенсивность, форму (`sharp`, `broad`, `shoulder`, `doublet`), тип источника (`manual`, `detector`, `image`) и, если доступно, небольшое окно исходного сигнала вокруг пика.
- Дополнительно передавать метаданные качества: `%T` или absorbance, ATR/KBr/плёнка/растворитель, baseline status, разрешение и предупреждения о возможных артефактах.
- Использовать существующий `app.js`/`jcampconverter` как единственный parser для JCAMP-DX/JCM (`.DX`, `.JCM`) в пользовательском приложении.
- Использовать корневой `peak.py` как детерминированный detector на уже нормализованных парах `wavenumber, signal`; не дублировать в Python JCAMP-парсер без необходимости.
- Для офлайн-проверок экспортировать нормализованные данные приложения в CSV/TSV и передавать их в `python peak.py`; для production лучше вынести detector в общий JS-модуль или передавать normalized data на backend.
- Проверять согласованность parser и detector на `exmaple/LABCALC.DX`, `exmaple/PE1800.DX`, `exmaple/SPECFILE.DX`, `exmaple/BRUKER1.JCM` и `exmaple/BRUKER2.JCM`; `FTIR_base.csv` использовать как справочную таблицу, а не как спектр.
- Сначала сохранить совместимость с текущим текстовым выводом, затем добавить `--json` для интеграции с backend.
- JSON должен содержать исходные `nu`, относительную заметность, класс интенсивности, FWHM, форму, параметры detector и предупреждения качества.
- Перед production добавить baseline correction, проверку равномерности сетки, поддержку нескольких серий/спектров, пропусков и калибровку `thresh/min-sep/FWHM` по эталонам прибора.
- Проверять detector на `exmaple/LABCALC.DX`, `exmaple/PE1800.DX`, `exmaple/SPECFILE.DX`, `exmaple/BRUKER1.JCM` и `exmaple/BRUKER2.JCM`; `FTIR_base.csv` использовать как справочную таблицу, а не как спектр.
- Не отправлять модели весь массив точек без необходимости: передавать detector-кандидаты, локальные окна и метаданные качества.

## Контракт LLM-интерпретации

- Серверный endpoint принимает подтверждённые пики и сопроводительные измерения, а не зависит от того, были ли они найдены вручную, JavaScript-detector или Python.
- `peak-db.js` остаётся только грубой локальной подсказкой для UI и не передаётся модели как источник истины.
- Канонический справочный контекст для LLM — `.ai/ftir-band-assignment/references/bands_master.md`; правила companion-полос, артефактов и отрицательных признаков — `diagnostic_zones.md`. При переносе в backend их нужно нормализовать в структурированные записи с provenance.
- Результат LLM хранится отдельно от пика: `interpretation`, `candidates`, `supporting_peaks`, `missing_evidence`, `confidence`, `sources`, `limitations`, `model` и `created_at`.
- Интерпретация не меняет координату и не переводит пик между `candidates` и `confirmed`; эти операции остаются ручными.
- Полный спектр передавать только по отдельной необходимости: для обычного анализа достаточно подтверждённых пиков, их признаков и локальных окон.

## Секреты, GitHub и деплой

- Frontend остаётся публичным и никогда не получает ключ Gemini/Mistral. Вызов идёт через backend/serverless endpoint `/api/analyze`.
- Локально использовать `.env` или `.env.local`, добавить их в `.gitignore`; в репозитории хранить только `.env.example` с пустыми именами переменных.
- В GitHub Actions хранить `GEMINI_API_KEY`/`MISTRAL_API_KEY` в `Settings -> Secrets and variables -> Actions`, использовать `${{ secrets.NAME }}` только как environment для deploy step и не выводить его в shell/log.
- Для Vercel/Netlify/Render/Fly.io задавать секрет в настройках проекта или secret manager, а не коммитить его в workflow, Dockerfile, compose-файл или frontend config.
- GitHub Actions должен деплоить backend с environment variable, но не собирать ключ в статический JS. Проверить итоговый bundle поиском по именам/префиксам токенов.
- Добавить GitHub secret scanning/push protection и ротировать ключ при любом подозрении на утечку. Не использовать production key в pull request из fork.
- Backend обязан иметь rate limit, ограничение размера тела, timeout, валидацию JSON, минимальное логирование и CORS только для домена приложения.
- В export/import session не сохранять API-ключи, authorization headers или полные prompts.

## Отложенный A/B-тест моделей

- Сравнить `gemini-3.5-flash-lite` с Gemma 4 26B A4B после стабилизации основного сценария.
- Использовать один и тот же набор подтверждённых пиков, `bands_master.md`, `diagnostic_zones.md` и JSON-контракт.
- Оценивать не только субъективное качество текста, но и: корректность диапазонов, companion-полосы, отсутствие выдуманных назначений, соблюдение ограничений по идентификации вещества, валидность JSON, задержку и расход лимита.
- Gemma подключать отдельным provider adapter только после проверки точного hosted/local endpoint и имени модели; не менять рабочий Gemini provider вслепую.
- Локальная проверка показала: текущий Gemini API-ключ видит `gemma-4-26b-a4b-it`, но API-вызов Gemma не поддерживает `thinkingBudget` и не завершил JSON в timeout 90 s. Для рабочего режима оставить `gemini-3.5-flash-lite`; Gemma тестировать через отдельный hosted/local endpoint или адаптер с управлением thinking.
- Сохранить обезличенные результаты тестов отдельно от пользовательских сессий; production-ключи и реальные спектры в benchmark не использовать.

## Compatibility gates

- Не переписывать существующий JCAMP/CSV parser и не менять формат `lastData`, `lastParsedRows`, `stripeSets` или session export без версии схемы и миграции.
- Новые поля пика (`width_cm1`, `intensity`, `shape`, `source`, `analysis`) делать необязательными. Старые stripes с `x`, `label`, `tip`, `color` должны продолжать загружаться и отображаться.
- Detector запускать отдельной явной командой; обычная загрузка файла и ручное добавление stripe не должны автоматически вызывать Python, backend или LLM.
- Backend error, timeout, отсутствие сети или невалидный ответ модели не должны блокировать график, ручные пики, экспорт CSV/PNG/SVG или импорт/экспорт сессии.
- До каждого изменения frontend сделать smoke-проверку: загрузка минимум одного `.DX` и `.JCM`, отображение графика, marker, ручной `Add stripe`, перенос candidate/confirmed, редактирование, удаление и экспорт.
- После добавления detector сравнивать исходные `lastData` и stripe behavior с baseline-версией на тех же примерах; новые вычисленные поля не должны менять координаты существующих ручных пиков.
- Backend и LLM покрывать mock-тестами, не использовать облачный вызов в обычных regression-тестах.
