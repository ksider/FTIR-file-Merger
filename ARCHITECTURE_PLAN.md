# План переделки архитектуры FTIR Analyzer

Дата создания: 2026-09-13
Последнее обновление: 2026-09-18
Статус: базовые этапы 1–4 реализованы; detector, baseline, привязка пиков к спектрам, comparison matrix и LLM-пайплайн работают. Следующий приоритет — выделить LLM-слой из `server.js`, закрепить pipeline интеграционными тестами и затем подключать reference spectra.

## 0. Результат аудита текущей структуры

### Клиент

- `index.html`, `styles.css` — статический интерфейс: загрузка файлов, график, таблица пиков/полос и блок ответа LLM.
- `app.js` — парсинг TXT/CSV/JCAMP-DX, объединение файлов в одну таблицу, отрисовка графика, ручная разметка полос, локальные сессии и запрос анализа.
- `config.js` — URL API и настройки графика/переводов.
- `peak-db.js` — локальная справочная база диапазонов FTIR.
- `exmaple/` — тестовые спектры.

Путь данных сейчас:

1. Файл читается браузером в `lastFilesRaw`.
2. `processFiles()` парсит все файлы и сводит их в общий `lastParsedRows`/`lastData`.
3. Ряд графика имеет `{ file, x, y }`, но ручная полоса в `stripeSets` хранит в основном только `x`.
4. `findNearestSpectrumPoint()` ищет ближайшую точку среди всех рядов. Поэтому выбор пика не является устойчивой сущностью конкретного спектра.
5. `buildConfirmedPeaksPayload()` отправляет `confirmedPeaks` и метаданные `spectrum.files/series`, но не отправляет точки спектров и не содержит `spectrumId` у пиков.

### Сервер

- `server/server.js` — HTTP API без фреймворка, rate limit, CORS, валидация JSON, загрузка справочников и прокси к LLM.
- `POST /api/analyze` принимает только подтверждённые пики.
- Провайдеры сейчас зашиты в один файл: `gemini`, `mistral`, `mock`.
- По умолчанию выбирается Google Gemini через `LLM_PROVIDER=gemini` в `.env`.
- `server/references/bands_master.md` и `diagnostic_zones.md` используются как справочник для prompt.
- `temp/skill_ru.md` и `temp/skill_en.md` в рабочий серверный pipeline не подключены; правила из них частично дублируются в `buildPrompt()`.

### Автоматический поиск пиков

- `temp/peak.py` — отдельный CLI на Python stdlib.
- Он умеет читать только одну пару колонок, сортировать данные, сглаживать простым скользящим средним и искать локальные максимумы.
- Для `%T` предусмотрено преобразование в `A`, но нет полноценной оценки baseline/prominence и нет интеграции с HTTP API.
- Расчёт FWHM и порога сейчас рассчитан преимущественно на сигнал с пиками вверх и не учитывает индивидуальную природу каждого спектра.

## 1. Целевая модель данных

Главное правило: каждый пик всегда принадлежит одному исходному спектру.

```json
{
  "schemaVersion": "2.0",
  "sample": { "id": "...", "name": "..." },
  "spectra": [
    {
      "id": "spectrum-1",
      "name": "before.dx",
      "signalType": "transmittance",
      "points": [[4000, 98.2], [3998, 98.1]],
      "preprocessing": { "baseline": "none", "smoothing": "savitzky-golay" }
    }
  ],
  "peakObservations": [
    {
      "id": "peak-spectrum-1-1715",
      "spectrumId": "spectrum-1",
      "nu": 1715.2,
      "prominence": 18.4,
      "height": 32.1,
      "widthCm1": 24.5,
      "fwhmCm1": 18.0,
      "shape": "sharp",
      "direction": "absorption",
      "detectionMethod": "automatic",
      "confidence": 0.91
    }
  ],
  "peakGroups": [
    {
      "id": "group-1715",
      "members": [
        { "spectrumId": "spectrum-1", "peakId": "peak-spectrum-1-1715" }
      ],
      "centerNu": 1715.2,
      "toleranceCm1": 8
    }
  ]
}
```

`peakGroups` — это не замена исходным наблюдениям, а слой сопоставления полос между спектрами. Если полоса есть только в одном спектре, это должно быть явно видно как отсутствие члена группы в других спектрах.

## 2. Новое разделение ответственности

### Клиент

- Хранить каждый загруженный спектр отдельно: `spectraById`.
- Использовать объединённый CSV только для экспорта, а не как основной источник истины.
- Для ручного пика сохранять `spectrumId`, ближайшую точку и локальное окно.
- Показывать, для какого спектра выбран пик; при перекрывающихся кривых дать явный выбор спектра.
- Запрашивать автоматические пики для всех спектров одной операцией.
- Показывать кандидаты отдельно по каждому спектру и позволять подтверждать/отклонять их.
- Передавать на анализ не только список `nu`, а структурированные наблюдения с привязкой к файлам.

### Сервер

Разделить API на два этапа:

1. `POST /api/peaks/detect`
   - вход: все спектры и настройки детектора;
   - действие: автоматический поиск пиков отдельно в каждом спектре;
   - выход: `peakObservations` с обязательным `spectrumId`, диагностикой и параметрами алгоритма.

2. `POST /api/analyze`
   - вход: все `peakObservations`, `peakGroups`, параметры образца и выбранные пользователем пики;
   - действие: сопоставление изменений между спектрами, подготовка компактного prompt и вызов выбранного LLM-провайдера;
   - выход: структурированный отчёт о пиках и межспектральных изменениях.

Сырые точки нужны детектору и могут передаваться ему. В LLM следует отправлять не весь график, а рассчитанные данные пиков всех спектров и компактные локальные окна только там, где они нужны для проверки.

## 3. Настраиваемый LLM-слой

Вместо логики провайдеров внутри `server/server.js` сделать единый интерфейс:

```text
provider.analyze({ prompt, responseSchema, settings }) -> normalizedResult
```

Отдельные адаптеры:

- `server/providers/gemini.js`;
- `server/providers/mistral.js`;
- `server/providers/openai-compatible.js` — для совместимых API;
- `server/providers/mock.js` — для тестов без сети.

Настройки из `.env`:

- `LLM_PROVIDER`;
- `LLM_MODEL`;
- `LLM_BASE_URL` для совместимого API;
- `LLM_TEMPERATURE`;
- `LLM_MAX_OUTPUT_TOKENS`;
- таймаут, размер запроса и лимит пиков.

API-ключи остаются только на сервере. В интерфейсе можно показывать безопасные настройки анализа: чувствительность детектора, допуск сопоставления, язык и режим вывода, но не ключи.

## 4. Анализ изменений и прохождения реакции

Текущая реализация уже формирует на сервере группы пиков и матрицу изменений до вызова LLM. Следующий подэтап — вывести эту матрицу в интерфейсе и использовать её в нормализованном ответе анализа.

Сервер до вызова LLM должен рассчитывать объективную сравнительную матрицу:

- пик присутствует/отсутствует в каждом спектре;
- смещение `Δν`;
- изменение относительной интенсивности/prominence;
- изменение FWHM и формы;
- новые и исчезнувшие полосы;
- группы полос, характерные для одной функциональной группы;
- качество сопоставления и предупреждения о разном масштабе/единицах.

LLM получает эту матрицу вместе с пиками всех спектров и справочником. Он не должен сам придумывать факт наличия пика.

Целевой ответ:

```json
{
  "reactionAssessment": {
    "status": "passed | not_passed | inconclusive",
    "summary": "...",
    "confidence": "high | medium | low",
    "evidence": [
      {
        "type": "disappeared_peak | appeared_peak | shifted_peak | intensity_change",
        "peakGroupId": "group-1715",
        "spectrumIds": ["before", "after"],
        "explanation": "..."
      }
    ],
    "missingEvidence": ["..."]
  },
  "spectra": [
    {
      "spectrumId": "before",
      "peakAssignments": [
        { "peakId": "...", "nu": 1715.2, "group": "C=O", "confidence": "medium", "reasoning": "..." }
      ]
    }
  ],
  "limitations": ["..."],
  "model": "...",
  "promptVersion": "..."
}
```

## 5. Автоматический детектор пиков

Выбранный вариант — Python worker с SciPy и `pybaselines`, при этом сохраняется fallback для локальной разработки без внешних зависимостей:

- вынести алгоритм из `temp/peak.py` в `server/peak_detector/peak_detector.py`;
- принимать JSON через stdin и возвращать JSON через stdout;
- Node-сервер запускает worker с ограничением времени и размера входа;
- SciPy используется для поиска пиков, а `pybaselines` — для adaptive baseline correction;
- при отсутствии библиотек worker не падает, а использует встроенный linear baseline и stdlib detector.

Базовый pipeline:

1. нормализовать сортировку X и определить `transmittance`/`absorbance`;
2. удалить NaN, дубликаты X и явно плохие точки;
3. лёгкое сглаживание с настраиваемым окном;
4. оценить baseline через `arPLS`/`airPLS`/`AsLS`/`SNIP`/`rubberband` или fallback-методом;
5. считать prominence относительно baseline;
6. найти минимумы для `%T` и максимумы для `A`;
7. объединить близкие кандидаты и сохранить shoulders, если они статистически устойчивы;
8. рассчитать prominence, относительную интенсивность, FWHM, ширину и форму;
9. присвоить confidence и вернуть исходное положение рядом со сглаженным;
10. выполнять это независимо для каждого `spectrumId`.

Параметры детектора должны быть частью запроса и результата: `smoothingWindow`, `minProminence`, `minSeparationCm1`, `maxPeaks`, `baselineMethod`, `baselineDegree`, `signalType`.

## 8. Критерии готовности

- У каждого автоматического и ручного пика есть `spectrumId` и стабильный `peakId`.
- Один и тот же `nu` в двух файлах не смешивается без явного `peakGroup`.
- LLM получает данные пиков всех спектров и сравнительную матрицу.
- Ответ может обоснованно сказать `passed`, `not_passed` или `inconclusive` и перечислить evidence.
- Можно сменить Gemini на другой поддержанный провайдер настройкой сервера.
- Автодетектор запускается через API, имеет настраиваемые параметры и тестируется без LLM.
- `server/.env` и ключи не попадают в Git.

## 9. Что не делать на первом этапе

- Не отправлять в LLM полный массив точек всех спектров без ограничения размера.
- Не давать LLM определять наличие пиков вместо математического детектора.
- Не объединять пики только по одинаковому `nu` без допуска и проверки формы/интенсивности.
- Не считать отсутствие пика доказательством реакции, если спектры несопоставимы по диапазону, масштабу или качеству.

## 10. Проверка Deep Picker и SciPy `find_peaks`

### Deep Picker

Под названием Deep Picker найденный основной проект — DEEP Picker Suite — предназначен для автоматического поиска пиков в 1D/2D NMR, а не для FTIR. Он возвращает координаты, интенсивности, параметры формы и confidence, но использует NMR-специфическую ANN-модель и C++-окружение. R-пакет `deeppicker` также описывает себя как интерфейс именно к NMR-инструментам.

Вывод: не использовать Deep Picker как готовый FTIR-детектор. Без размеченной FTIR-выборки и отдельной переобученной модели это добавит тяжёлую зависимость, но не даст доказуемого улучшения. К нему можно вернуться позже как к исследовательской ML-ветке, если появятся сотни/тысячи размеченных FTIR-спектров с пиками.

### SciPy `scipy.signal.find_peaks`

`find_peaks` подходит как базовый детектор: он поддерживает `distance`, `prominence`, `width`, `height`, `threshold`, `wlen` и возвращает рассчитанные свойства пиков. Это напрямую закрывает большую часть требований к первому серверному детектору.

Ограничения, которые нужно учесть в адаптере:

- функция ищет локальные максимумы; для `%T` нужно сначала преобразовать сигнал в absorbance либо искать пики через `find_peaks(-signal)` после baseline correction;
- она не выполняет сама baseline correction, сглаживание, ресэмплинг и определение типа сигнала;
- `distance` задаётся в отсчётах, поэтому его нужно переводить из cm⁻¹ с учётом шага конкретного спектра;
- NaN нужно удалить до вызова;
- для широких FTIR-полос нужно использовать `prominence`, `width` и достаточно большой `wlen`, а не только локальный максимум;
- параметры должны быть сохранены в результате, чтобы анализ можно было воспроизвести.

### Решение для реализации

Взять SciPy `find_peaks` как основной механизм candidate peak picking в Python worker. Вокруг него добавить:

1. проверку и нормализацию данных;
2. baseline correction;
3. лёгкое сглаживание;
4. инверсию `%T` или преобразование в `A`;
5. перевод минимального расстояния из cm⁻¹ в samples;
6. расчёт формы и confidence;
7. ручное подтверждение кандидатов в интерфейсе.

Таким образом, детекция остаётся объяснимой и настраиваемой, а Deep Picker не блокирует первый релиз.

## 10.1. Открытая база эталонных IR/FTIR-спектров

Для поиска похожих эталонов нужно отделить базу спектров от локальной базы
подсказок `peak-db.js`. `peak-db.js` остаётся справочником диапазонов и
функциональных групп, а библиотека эталонных кривых используется для
численного сравнения экспериментального спектра с известными образцами.

### Источники

- Основной кандидат — NIST Chemistry WebBook (SRD 69): публичный источник с
  более чем 16 000 IR-спектров и поиском по названию, формуле, CAS и структуре.
  Это не OSI-лицензированный open-source пакет: перед зеркалированием или
  массовой загрузкой нужно соблюдать условия NIST, сохранять атрибуцию и
  источник для каждого спектра.
- Для управляемого локального импорта можно изучить `muCommons/NistChemData`:
  проект автоматизирует извлечение данных WebBook, но прямо требует принять
  условия использования NIST; сгенерированные спектры не следует добавлять в
  репозиторий без отдельной проверки прав.
- Наборы вроде `xpectrass` полезны для тестов и будущего ML (например, наборы
  полимеров), но не заменяют химически атрибутированную reference-библиотеку.
- Dataset [IR-NMR Multimodal Computational Spectra Dataset for 177K
  Patent-Extracted Organic Molecules](https://zenodo.org/records/16417648)
  подходит как масштабный вычислительный reference/ML-источник: 177 461
  молекула, Parquet-чанки, ось частот до 4003.17 cm⁻¹ с шагом около 0.3336
  cm⁻¹, `SMILES`, идентификатор молекулы и массив `ir_spectra`.

Для этого набора нужно явно хранить тип `computed`, а не `experimental`:
спектры рассчитаны из MD/DFT/ML-пайплайна и приближены к 300 K. У них нет
гарантированной совместимости с фазой образца, ATR/пропусканием, прибором,
разрешением и baseline экспериментального FTIR. Поэтому они годятся для
генерации кандидатов и будущего обучения, но не для автоматического вывода о
наличии вещества или прохождении реакции.

Лицензию нужно разделять по объектам: Zenodo указывает CDLA Permissive 2.0
для данных, включая обязанность приложить текст соглашения при распространении;
сопроводительный ChemRxiv-препринт имеет CC BY-NC-ND 4.0 и должен цитироваться
отдельно. Не смешивать эти условия и не переименовывать вычислительные данные
в экспериментальные.

### Предлагаемая интеграция

1. Добавить серверный адаптер `server/reference_spectra/` с единым форматом:
   `id`, `source`, `sourceUrl`, `license`, `compoundName`, `cas`, `formula`,
   `signalType`, `xUnit`, `points` и `metadata`.
2. Для Zenodo хранить manifest версии, DOI, список 9 Parquet-чанков, размеры и
   checksums. Не помещать 8+ GB датасета в git, Docker image или browser bundle;
   загрузка должна быть отдельной командой/volume с явным согласием оператора.
   Сервер получает путь к данным через `REFERENCE_SPECTRA_DIR`, а наличие
   набора включается отдельной настройкой `REFERENCE_SPECTRA_ENABLED`.
3. Построить offline-индекс: привести вычислительные спектры к общей сетке,
   сгладить/нормализовать, сохранить компактный downsample/vector и метаданные.
   Полный Parquet читать только при обновлении индекса или открытии результата.
4. Не отправлять всю библиотеку в браузер. Серверные endpoints:
   `GET /api/reference-spectra/search` для метаданных и top-N совпадений,
   `GET /api/reference-spectra/:id` для выбранной кривой.
5. Нормализовать эталон и пользовательский спектр одинаково: диапазон,
   направление оси, единицы, resampling, baseline и нормализация интенсивности.
6. Ранжировать кандидатов математически: cosine/корреляция, расстояние по
   первой производной и штраф за несовпадающие области. LLM получает только
   top-K кандидатов, score, метаданные и локальные совпадения пиков.
7. В интерфейсе добавить действие `Find reference matches`: список кандидатов,
   score, источник/лицензия и кнопку наложения эталона на график.
8. Кэшировать результаты по хэшу нормализованного спектра и версии алгоритма;
   хранить provenance, чтобы каждый вывод можно было воспроизвести.

Принятое решение для проекта: этот Zenodo-набор подключать как отдельный
опциональный ресурс только на сервере. Архив и построенный индекс хранятся в
volume или другой внешней директории deployment, не попадают в Git,
frontend или Docker image. Если reference-база недоступна, основной анализ
пиков и LLM-анализ должны продолжать работать.

Сценарий использования — помощь в распознавании: сервер возвращает top-K
похожих вычислительных спектров, а интерфейс показывает их как гипотезы с
оценкой сходства, SMILES и provenance. Это не точное автоматическое
определение вещества. Reference match является дополнительным evidence и не
должен автоматически подтверждать наличие вещества или прохождение реакции.

## 10.2. Найденные проблемы текущего detector pipeline

Перед дальнейшим подбором параметров нужно исправить несколько алгоритмических
проблем, иначе интерфейс будет только скрывать источник ошибок:

- adaptive `arPLS` может принять широкую OH/NH-полосу за фон; broad-pass её
  сохраняет частично, но это должно быть явно видно в результате и диагностике;
- кандидат broad-pass получает prominence от broad-сигнала, а FWHM сейчас
  рассчитывается по fine corrected-сигналу. Из-за этого ширина может быть
  несопоставимой или скачкообразной;
- `x_step` берётся как минимальный шаг. На неравномерной сетке это завышает
  `distance` в отсчётах; нужен устойчивый медианный шаг и контроль выбросов;
- нет отдельного контроля атмосферного CO₂ около 2350 cm⁻¹ и низкочастотных
  артефактов. Такие кандидаты должны маркироваться как possible artifact или
  исключаться настройкой диапазонов, а не трактоваться как реакция;
- merge fine/broad-кандидатов зависит от разрешения исходного файла, потому что
  расстояния переводятся в samples. Сравнение и слияние должны выполняться в
  cm⁻¹ после нормализации сетки;
- `confidence` сейчас нормируется относительно самого сильного кандидата в
  текущем спектре и потому не является межспектральной вероятностью;
- нужны контрольные тесты для широкой OH-полосы, узкого пика, плеча, CO₂,
  неравномерного шага, `%T` 0–100 и `%T` 0–1.

Порядок исправления: сначала корректность источника кандидата и FWHM, затем
устойчивый шаг/merge, затем artifact masks и только после этого подбор
порогов для конкретных спектров крахмала и АКД.

Уже исправлено в текущей реализации: для неравномерной сетки используется
медианный шаг; fine/broad-кандидаты объединяются в координатах cm⁻¹; ширина
считается на том же corrected-сигнале, на котором найден кандидат, с
интерполяцией по реальной x-сетке. Кандидатам добавляются неразрушающие
`qualityFlags` для возможного атмосферного CO₂, низкочастотного артефакта и
неопределённой ширины. Поиск дополнительно ограничивается текущим видимым
диапазоном X. Колесо масштабирует график относительно текущих границ осей и
не сбрасывает пользовательский диапазон.
Окончательный фильтр артефактов и отдельные тесты на реальных спектрах
крахмала остаются следующим подэтапом.

## 11. План реализации по шагам

### Фаза 0 — зафиксировать требования и контрольные сценарии

До написания нового кода определить минимальные пользовательские сценарии:

- загрузить один спектр и автоматически получить пики;
- загрузить несколько спектров до/после;
- увидеть пики, принадлежащие каждому файлу;
- вручную исправить или подтвердить кандидат;
- сравнить появившиеся, исчезнувшие, смещённые и изменившие интенсивность полосы;
- отправить все подтверждённые данные в LLM;
- получить вывод о реакции с доказательствами и уровнем уверенности;
- экспортировать спектры, пики, настройки и отчёт.

На этой фазе также зафиксировать единицы, тип сигнала (`%T`/`A`), допустимые размеры файлов и правила определения ролей спектров: например, `before`, `after`, контроль и повтор.

### Фаза 1 — тестовый контракт данных

- Добавить JSON-схему `schemaVersion: 2.0`.
- Сделать fixtures для одного спектра, пары до/после, отсутствующего пика, сдвига пика и шума.
- Реализовать общую валидацию на сервере.

### Фаза 1A — локальное состояние frontend

Frontend хранит два связанных объекта в `localStorage`:

- настройки интерфейса, которые должны переживать очистку рабочей сессии и
  отсутствие загруженных файлов: язык, имя файла, sample index, detector и
  baseline-параметры, диапазоны графика, видимость серий, выбранный набор пиков,
  свёрнутое состояние таблицы и текущий маркер;
- рабочую сессию с исходными файлами, спектрами, ролями, названиями, Y-сдвигами,
  ручными и автоматическими пиками, текстами/назначениями, отчётом LLM,
  применённой baseline и диагностикой обработки.

Сессия версии 2 сохраняет совместимость с чтением версии 1. Ключи API и другие
секреты в локальное состояние не попадают. Кнопка очистки удаляет оба объекта.
- Описать API `/api/peaks/detect` и `/api/analyze`.
- Не менять внешний вид приложения, кроме временных диагностических элементов.

Результат фазы: можно проверить новый pipeline без зависимости от окончательного интерфейса.

### Фаза 2 — Python/SciPy detector

- Вынести детектор в `server/peak_detector/`.
- Подключить SciPy `find_peaks`.
- Добавить preprocessing, baseline, обработку `%T`, FWHM, prominence и confidence.
- Запускать детектор отдельно для каждого `spectrumId`.
- Добавить endpoint `/api/peaks/detect` и mock-режим.
- Протестировать на fixtures и имеющихся файлах из `exmaple/`.

Результат фазы: сервер возвращает корректные пики по каждому спектру, а не общий список независимых координат.

### Фаза 3 — подготовка доменной модели клиента

- Отделить парсинг и обработку данных от DOM-кода.
- Ввести модули `spectrumModel`, `peakModel`, `comparisonModel`, `sessionModel`.

- Подключить автоматические кандидаты и подтверждение пользователем.

На этой фазе старый интерфейс ещё можно оставить работающим через адаптер. Это даст возможность проверять новую модель без одновременной переделки всех экранов.

### Фаза 4 — точка смены интерфейса

Именно здесь нужно менять интерфейс. К этому моменту уже должны быть стабильны:

- сущности спектра и пика;
- ответ detector API;
- правила группировки полос между спектрами;
- payload и схема ответа анализа;
- список основных пользовательских сценариев.

Менять UI раньше невыгодно: компоненты будут строиться вокруг старого неправильного состояния, и их придётся переделывать после появления `spectrumId`, автоматических кандидатов и сравнительной матрицы.

До начала этой фазы пользователь подготавливает список желаемых изменений интерфейса. Список желательно разделить на:

1. что должно быть видно постоянно;
2. какие инструменты нужны в рабочей области;
3. какие панели должны быть боковыми/сворачиваемыми;
4. что относится к одному спектру, а что ко всей серии;
5. как выглядит сравнение до/после;
6. что должно быть доступно на мобильном экране;
7. какие действия должны быть быстрыми и в один клик.

### Фаза 5 — миграция интерфейса на shadcn-подобную систему

Если выбирается настоящий shadcn/ui, клиент лучше перенести на React + Vite + Tailwind CSS. shadcn/ui — это набор исходников компонентов, а не подключаемая CSS-тема, поэтому простого добавления одного файла стилей к текущему `index.html` недостаточно.

Предлагаемая структура нового клиента:

```text
frontend/
  src/
    app/
    components/
      spectrum-chart/
      spectrum-list/
      peak-table/
      detector-settings/
      comparison-panel/
      analysis-report/
    domain/
    api/
    i18n/
```

Новый layout:

- верхняя панель: проект/образец, загрузка, экспорт, запуск анализа;
- левая панель: список спектров, роли `before/after/control`, видимость и настройки;
- центральная область: большой график с режимами overlay/stacked/difference;
- правая панель: настройки детектора, кандидаты и подтверждение пиков;
- нижняя/выдвижная панель: сравнение полос и отчёт LLM.

Сначала собрать только shell и подключить реальные данные. Затем переносить инструменты по одному: график, список спектров, detector settings, peak table, comparison, report. D3 можно временно оставить внутри отдельного `SpectrumChart`-компонента.

- Контракт API v2 и JSON Schema: реализованы базовые версии.
- Клиентская модель отдельных спектров: реализована внутри текущего `app.js`,
  но ещё не разделена на отдельные доменные модули.
- Привязка ручных и автоматических пиков к `spectrumId`/`peakId`: реализована.
- SciPy detector и adaptive baseline: подключены через Python worker.
- Сравнение спектров, comparison matrix и новый LLM payload: подключены.
- Дополнительный пользовательский prompt: подключён, ограничен 2000 символами.
- Текущий интерфейс: fieldset-перестройка и рабочие вкладки реализованы; полный
  перенос на React + настоящий shadcn/ui ещё не выполнен.
- Серверный `/api/peaks/detect` и временные диагностические контролы клиента: реализованы.
- Python peak worker с SciPy-путём и stdlib fallback: реализован; SciPy включается в Docker через `server/requirements.txt`.
- `pybaselines` для adaptive baseline correction: подключён; добавлены режимы `arPLS`, `airPLS`, `AsLS`, `SNIP`, `rubberband`, `linear`, `none`.
- Диагностика baseline/corrected: возвращается сервером с ограниченным downsample до 1200 точек.
- Диагностическая привязка автоматических кандидатов к спектрам: реализована в текущем UI до большой shadcn-миграции.
- Не ломать текущий ручной режим: автоматические пики должны быть дополнительным источником кандидатов.
- Выбор ролей `before`/`after` в интерфейсе: реализован в popup настроек
  спектра; при отсутствии роли `before` базовым остаётся первый спектр.
- Reference spectra adapter и offline-индекс Zenodo: пока только спроектированы,
  архив отдельно на сервер не загружался.
- Вынос LLM-провайдеров и prompt из `server.js`: ещё не выполнен.
- Основные заголовки и типы изменений отчёта переведены через i18n; API-
  интеграционные тесты, полный i18n динамических ответов и тесты detector на
  реальных примерах ещё требуют доработки.

Дополнительно реализовано после первоначальной записи этого статуса:

- ручной пик сначала получает локальную оценку, затем может быть уточнён
  сервером через `manualMeasurements`, не меняя вручную поставленную координату;
- для отсутствующих значений ширины/FWHM больше не отображается ложный `0.00`:
  используется `—` и диагностический `qualityFlag`;
- восстановление и сохранение локальной сессии включает роли спектров,
  baseline/diagnostics, настройки отображения, ручные и автоматические пики,
  пользовательский prompt и результат анализа;
- сервер логирует запросы detector и LLM, параметры prompt, finish reason и
  ошибки невалидного JSON; лимит ответа и timeout LLM задаются через `.env`;
- запрос к LLM больше не переключает автоматически набор `Candidates` на
  `Confirmed` и не должен менять текущий контекст отображения диаграммы.
